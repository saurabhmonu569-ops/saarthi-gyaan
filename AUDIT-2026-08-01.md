# SAARTHI — Full System Audit

**Date:** 01 Aug 2026, 16:35 IST
**Scope:** RAG pipeline, worker security, performance, accessibility, release process
**Method:** Static code read + live log analysis + artifact inspection + upstream doc research

---

## 0. Executive Summary — one paragraph

SAARTHI's answer-quality problem is **not** a prompt problem. The system prompt already
forbids fabricated shlokas, forbids medical advice, and forbids inventing citations. The
failure is structural, in three stacked layers:

1. **The semantic search engine has never run.** The embedding model file is a 134-byte
   Git LFS pointer, not a model. `semanticSearch()` is fail-soft, so it silently returns
   an empty array and the app falls back to Devanagari substring matching.
2. **The relevance guard cannot reject anything.** It is defined relative to the top
   score, so a uniformly-irrelevant result set passes untouched — and the first three
   results bypass it entirely.
3. **Citations are decoupled from grounding.** The `📚 Aadhaar` footer is built from
   whatever chunks were retrieved, regardless of whether the answer used them.

The result the user sees: every answer carries confident scripture citations, the same
four or five books rotate through unrelated questions, and the model — running on a weak
engine because Gemini is quota-exhausted — fills the gaps with invention.

## 2. Findings — AI / RAG Engineer

### P0-1 — Embedding model is a Git LFS pointer, not a model

**Evidence**

```
public/embed-model/paraphrase-multilingual-MiniLM-L12-v2/onnx/model_quantized.onnx
→ 134 bytes

version https://git-lfs.github.com/spec/v1
oid sha256:66fc00f5f29afcaff34092e1bdd20008ca3918265a82fb9695a551e510cc4ebc
size 118308126
```

`.gitattributes` confirms only this one file is LFS-tracked. The real artifact is 118 MB
and is not present on disk.

**Consequence** — `semanticSearch.js:151-154` catches the load failure and returns `[]`.
By design this never throws and never surfaces to the user:

```js
} catch (e) {
  console.warn("[SemanticSearch] search failed, keyword-only fallback used:", e);
  return [];
}
```

So retrieval has been **100% keyword-based** since the feature shipped. The
"real semantic search fix (2026-07-26)" has never executed in production.

**Why this explains the user's exact complaints**

| Complaint | Mechanism |
|---|---|
| "Same source baar-baar aata hai" | Keyword search matches Devanagari substrings only. Hinglish and paraphrased questions match almost nothing, so whichever chunks score on common words win every time. |
| "Sabko read nahi karta" | Correct observation. The mechanism that would read across all 24 books is offline. |
| "Sahi source ke saath 100% perfection" | Not achievable in the current state. |

**Fix** — decided: move query embedding server-side to Cloudflare Workers AI
(`@cf/baai/bge-m3`), re-embed the corpus, ship int8-quantized vectors.

### P0-2 — Relevance threshold is relative, therefore incapable of rejecting

`src/views/ChatView.jsx:343-352`

```js
const topScore = sorted.length ? sorted[0].score : 0;
const MIN_RELATIVE_SCORE = 0.35;
...
if (!hintedBook && diverse.length >= 3 && r.score < topScore * MIN_RELATIVE_SCORE) continue;
```

Two independent defects in one line.

**(a) Scale-invariance.** The cutoff is `topScore × 0.35`. If the best match is garbage
(say 0.12), the cutoff becomes 0.042 and everything passes. A relative threshold can
enforce *diversity*; it can never enforce *relevance*. It is blind precisely in the case
that matters — when the whole result set is bad.

**(b) First-three amnesty.** `diverse.length >= 3` means the first three chunks are
admitted with no check at all. **This is the direct cause of every answer carrying a
citation**, regardless of topic.

The code comment at lines 330-342 shows this guard was added to fix "Guru Granth Sahib
appears in every generic answer." That was a relevance symptom treated with a diversity
instrument, which is why it only half-worked.

---

### P0-3 — Incommensurable score scales are compared numerically

`src/views/ChatView.jsx:264-266`

```js
for (const r of [...crossFlat, ...kwResults, ...semResults]) {
  const existing = byId.get(r.chunk.id);
  if (!existing || r.score > existing.score) byId.set(r.chunk.id, r);
}
```

Three different units enter this comparison:

| Source | Formula | Range |
|---|---|---|
| keyword (`engine.js:388`) | `(s / keywords.length) * (0.5 + 0.5*density)` | its own 0–1 scale |
| semantic (`semanticSearch.js:147`) | cosine dot product | −1 … 1 |
| book-overview (`ChatView.jsx:301`) | hardcoded `0.05` | constant |

Comparing them with `>` is comparing kilograms to kilometres. Even after semantic search
is restored, a keyword score of 0.8 will outrank a cosine of 0.6 that represents a
genuinely better match. **Any absolute threshold must therefore be applied per
`match_type`, not globally.**

### P1-4 — Synthetic low-score chunks are force-injected

`src/views/ChatView.jsx:296-302` — when a book is named but fewer than 3 chunks match, the
code injects an evenly-spaced sample of that book at `score: 0.05`. This guarantees
grounding-shaped context that carries no actual relevance, and those chunks then feed the
citation footer.

### P1-5 — Citation footer is decoupled from grounding

`src/hooks/useChat.js:413-429` — the footer is assembled from `liveChunks` whenever they
exist and the answer lacks an explicit "no direct reference" disclaimer. Whether the model
actually used those passages is never established. The user is shown a provenance claim
the system cannot support.

### P1-6 — Devanagari self-citation is not stripped

`src/hooks/useChat.js:382-384`

```js
.replace(/\n*📚\s*\*?Aadhaar[^\n]*/gi, "")
.replace(/\n+[*_]{0,2}\s*Aadhaar\s*:[^\n]*/gi, "")
```

Both patterns match the Latin string `Aadhaar` only. The model frequently emits Devanagari
`आधार:` (and the misspelling `आदार:`). Those survive, producing answers with two
contradictory source lists — one inline, one in the footer.

Observed live:

```

📚 Aadhaar: Valmiki Ramayana · Yajurveda · Samaveda · Narasimha Purana
```

## 3. Findings — Security Auditor

### ✅ Correct

- **Origin allowlist is exact-match** (`worker:589`) — no wildcard, no prefix matching, no
  `null` origin acceptance. Correct.
- **Session tokens are HMAC-signed and verified server-side** (`worker:304`) — the
  2026-07-26 fix genuinely closed the localStorage-spoofing hole.
- **Rate limiting is KV-backed and global** (`worker:117-140`), 20/min, fails open by
  design and documented as such.
- **VAPID private key is a Secret**, public key plaintext. Correct split.

### P1-10 — Rate-limit keys pollute the push namespace and are iterated by cron

`worker:848`

```js
const page = await env.PUSH_SUBS.list({ cursor, limit: 100 });
```

`PUSH_SUBS` holds two unrelated key families: `sub:*` (subscriptions) and `rl:*`
(rate-limit counters, 60s TTL). The scheduled job lists **all** keys. For an `rl:` key the
value is `"2"`, which `JSON.parse` accepts, yielding `rec = 2`; then
`sendWebPush(rec.subscription /* undefined */)` throws internally and is counted as a
**failed push**.

Impact: inflated failure counts, wasted subrequests against the free-plan cap. Intermittent
because `rl:` keys expire in 60s.

**Fix** — one line: `list({ cursor, limit: 100, prefix: "sub:" })`.

### P2-11 — Subscription metadata is client-asserted, not session-derived

`worker:650-656` stores `email` and `name` straight from the request body, even though a
verified session token is already available in the same handler (`worker:603-612`). A
caller from an allowed origin can attribute a subscription to any email.

Impact is low (personalisation only), but the verified identity is right there and unused.

## 4. Findings — Performance Engineer

### P0-12 — First-visit payload is 171 MB, and it does not work

| Asset | Size |
|---|---|
| `model_quantized.onnx` | 118.5 MB |
| `tokenizer.json` | 16.3 MB |
| `ort-wasm-simd.wasm` | 9.6 MB |
| `vectors.bin` | 26.5 MB |
| **Total** | **≈ 171 MB** |

On the chosen path (Workers AI + int8 vectors) this becomes **17.7 MB** — a 90% reduction —
while also being the version that actually functions.

| | Now | After |
|---|---|---|
| Model | 118.5 MB | 0 |
| Tokenizer | 16.3 MB | 0 |
| WASM | 9.6 MB | 0 |
| Vectors | 26.5 MB (384d f32) | 17.7 MB (1024d int8) |

**Cost check** — Workers AI free tier is 10,000 neurons/day; `bge-m3` bills 1,075 neurons
per 1M input tokens. At ~20 tokens per query that is **≈465,000 queries/day free**.
One-time corpus re-embed: 18,083 chunks × ~200 tokens = 3.62M tokens ≈ **3,888 neurons** —
inside a single day's free allocation.

### P2-13 — Whole keyword corpus is resident in browser memory

18,494 chunks are loaded client-side. Acceptable today; a candidate for server-side search
(Vectorize) in a later phase.

### P2-14 — Push fan-out is sequential with a hard ceiling

`worker:846-865` — `MAX_PER_RUN = 300`, sequential `await` per subscriber. Already noted in
code comments as a scaling limit. Fine at current scale; needs batching + `waitUntil`
before growth.

## 9. Kill Criteria

Explicit conditions under which the chosen approach should be abandoned rather than
defended:

| Decision | Abandon if |
|---|---|
| Workers AI embedding | p95 `/embed` latency > 400 ms, or free-tier neurons prove insufficient in practice → fall back to a small client-side model with int8 vectors |
| int8 quantised vectors | Recall on the B1 benchmark drops > 5% vs float32 → revert to float32 and accept 70 MB, or move search to Vectorize |
| `bge-m3` | Hindi retrieval quality does not beat the current keyword baseline on the B1 test set → re-evaluate `qwen3-embedding-0.6b` |
| Keeping Groq primary | Prompt-rule violations persist after B2/B3 land → Gemini quota becomes a P0 blocker, not a P2 |

---

## 10. The one-line version

**Push notifications work. Answer quality does not, because the search engine that was
supposed to read the 24 books has never once been loaded — and the guard rails that should
have caught that were written in units that can never fail.**
